# M8 — Release Engineering Plan (part 1)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything of the M8 release work that needs no secrets and no product decision: one workspace version shown by both programs, icons made at packaging time, packages and checksums for three platforms, the update manifest, a reproducible-build check, local crash reports, and the release and CI workflows. Signing, notarisation and publishing are wired in but run only when the product owner supplies the secrets.

**Architecture:**
- `fluut-core` (layer 6): `build_info` (version and git commit, from `build.rs`) and `crash` (panic hook, report files, offer on next start). Both programs use them; `fluut-cli` and `fluut-app` change only in `main.rs`, the About dialog and one test.
- `xtask`: new tasks `icons`, `version`, `package`, `checksums`, `manifest`, `rustflags`, `repro-check`, in modules `icons`, `archive` (deterministic tar.gz and zip), `package`, `manifest`, `repro`, `util`.
- `.github/workflows/`: `release.yml` (new), `audit.yml` (new), `ci.yml` (`docs`, `repro` jobs).

**Tech Stack:** as M7. Added to `xtask` only: `resvg` 0.49 (as in `fluut-app`'s build script), `png` 0.18, `flate2` 1 (all already in `Cargo.lock`), and the workspace's `sha2` and `crc32fast`. ICO and ICNS are written by hand around PNG images, so no `ico` or `icns` crate. No new licences.

**Design:** [D14](../design/D14-build-test-release.md) §2, §3, §5, §6, §7; spec 06 §6.2–§6.5.

## Global Constraints

All earlier Global Constraints apply. In addition:

- No secrets and no invented certificates. Every signing step is guarded and unsigned builds work.
- Nothing is ever sent from a user's computer: crash reports are local files.
- Generated icons are never committed.
- The workflow YAML cannot be run here; it is checked by parsing and by running its scripts' parts locally where possible. The plan says which parts are untested.
- Do not modify `fluut-cam`, `fluut-io-*`, `fluut-sim`, `fluut-script` or `third_party/`; `fluut-app` only for the version, icon and crash hook. No DeskProto-derived content.

## Scope decisions

- **Window icon:** `fluut-app`'s `build.rs` already rendered `fluut-D-icon-stock.svg` for the window icon (M5). It stays as it is; a test in `xtask` checks that both use the same master.
- **Archives are written by `xtask`**, not by `tar`, `zip` or `Compress-Archive`, so they are the same bytes on every runner and the workflow needs no platform tools for them.
- **Draft releases:** the workflow ends with a draft GitHub release. A person publishes it. The "latest release" that the next run reads `releases.json` from is therefore always a published one.
- **Secret checks:** `secrets` cannot be used in a step `if`. The first job turns "is this secret set" into outputs; each signing step tests an output and gets its secrets in its own `env`, so no step that builds code sees a secret.
- **Crash dialog:** the in-window offer waits for the translated texts (the i18n work owns `text.rs`). The app writes the note to stderr for now.

## Review Focus

1. **Guards:** with no secrets set, every step that needs one is skipped and the workflow still ends in a draft release. With secrets, a failed signature check fails the job.
2. **Archives:** the same input gives the same bytes; the zip and tar readers in the tests parse the writers' output independently.
3. **Crash reports:** no project data, no network, a failing write never causes a second panic.

### Task 1: Version and build information

**Files:** Create `crates/fluut-core/{build.rs, src/build_info.rs}`; modify `crates/fluut-core/src/lib.rs`, `crates/fluut-cli/src/main.rs`, `crates/fluut-app/src/ui/about.rs`.

- One version: `[workspace.package]` (already in place; every crate inherits it). `build_info::version_string()` is `0.1.0 (d4af3c037012)` or `0.1.0`. `fluut --version` prints it; the About dialog shows the commit under the version.
- The release profile of D14 §2 (`lto = "thin"`, `codegen-units = 1`, `panic = "unwind"`) was already in the root `Cargo.toml`; no change.
- [x] **Step 1:** Tests: formatting with and without a commit, version equals the workspace version, the commit is hexadecimal, `fluut --version` output.
- [x] **Step 2:** Implement; `build.rs` takes `FLUUT_GIT_COMMIT` or `git rev-parse`, and reruns when `HEAD` or the reflog changes (also in a linked worktree).

### Task 2: Icons at packaging time

**Files:** Create `xtask/src/icons.rs`.

- `cargo xtask icons <out-dir>` renders the master at every size and writes `windows/fluutcam.ico` (16–256), `macos/fluutcam.icns` (16–1024, the PNG element types) and `linux/hicolor/<N>x<N>/apps/fluutcam.png` (16–512).
- [x] **Step 1:** Tests: PNG size, transparent corners and ink colour; deterministic output; ICO directory offsets and the 256 → 0 rule; ICNS element lengths; `generate` writes every file; the app's build script uses the same master.
- [x] **Step 2:** Implement. Checked by loading the `.ico` with `System.Drawing.Icon` on Windows.

### Task 3: Packages and checksums

**Files:** Create `xtask/src/{archive.rs, package.rs, util.rs}`.

- `archive`: tar.gz (ustar, sorted, fixed mtime, no owners, gzip header without time stamp) and zip (deflate, sorted, fixed DOS time).
- `package --platform {windows-x86_64,linux-x86_64,macos-universal} --bin-dir --icons --out`: Windows zip, Linux tarball (with `.desktop` file and icons), macOS `FluutCAM.app` tree (with `Info.plist`) plus the CLI tarball. `checksums <dir>` writes `SHA256SUMS`.
- [x] **Step 1:** Tests: both archive formats read back independently (tar headers and checksums; zip central directory, inflate, CRC); sorting and determinism; layouts per platform; the plist; missing inputs name the file; `sha256sum` format.
- [x] **Step 2:** Implement.

### Task 4: Update manifest

**Files:** Create `xtask/src/manifest.rs`; D14 §5.3 documents the format.

- `manifest --dist --base-url --out [--previous]`: format `fluut.releases/1`, newest release first, artefacts with platform, kind, URL, SHA-256, size and minimum OS.
- [x] **Step 1:** Tests: artefact names parse; one release lists only its own version's artefacts, sorted; URL, hash, size and `min_os`; the documented shape; a new release goes first and replaces its own version; a foreign format is refused; version order with pre-releases.
- [x] **Step 2:** Implement.

### Task 5: Reproducible builds

**Files:** Create `xtask/src/repro.rs`.

- `rustflags` prints the release flags (path remapping of the checkout and `CARGO_HOME`; control-flow guard on Windows). `repro-check` builds `fluut` twice from scratch with `--locked`, `SOURCE_DATE_EPOCH` and those flags, and compares SHA-256.
- [x] **Step 1:** Tests: flags per platform; the comparison reports equal and different builds.
- [x] **Step 2:** Implement. Finding: `ahash` (through `rhai`) draws constants at compile time with `const-random`, which made every build differ in 169 places; a fixed `CONST_RANDOM_SEED` removes them. On Windows, 20 bytes still differ: the PE time stamp (a hash of the content) and the 16-byte PDB GUID in the debug directory, both derived from the PDB. Not pursued; the D14 check is the Linux job, which has not run.

### Task 6: Crash reports (local)

**Files:** Create `crates/fluut-core/{src/crash.rs, tests/crash.rs}`; modify both `main.rs`.

- Panic hook writes `crash-<time>-<pid>.txt` to `<data dir>/crashes`; the next start tells the user, and `fluut` in a terminal offers to print it. Reports are then renamed `….seen.txt`. No sending code.
- [x] **Step 1:** Tests: data dir per platform and the `FLUUT_DATA_DIR` override; report text; pending and seen files; the offer with yes, no and not asking; a real panic in a test process leaves a report with message, location and backtrace; `fluut` announces an earlier report once.
- [x] **Step 2:** Implement.

### Task 7: Workflows

**Files:** Create `.github/workflows/{release.yml, audit.yml}`, `.cargo/audit.toml`; modify `.github/workflows/ci.yml`.

- `release.yml` on tags `vX.Y.Z*`: `check` (tag equals workspace version, `SOURCE_DATE_EPOCH` = commit time, which secrets exist), `build` (four targets, locked, release flags, Authenticode signing and verification on Windows), `package-portable` (Windows zip, Linux tarball), `package-macos` (`lipo`, app bundle, Developer ID or ad-hoc signing, DMG, notarisation and stapling, verification), `release` (SBOM with `cargo-cyclonedx`, manifest, checksums, minisign, draft release).
- `ci.yml`: `docs` job; `repro` job (main, tags, manual); `workflow_dispatch`. `audit.yml`: daily `cargo audit`.
- [x] **Step 1:** Parse the YAML; run the scripts' parts locally (below).
- [x] **Step 2:** D14 and the plan README updated.

**Done.** One workspace version (with the git commit) shows in `fluut --version` and the About dialog. `cargo xtask` now renders the app icon to ICO, ICNS and PNG, writes byte-reproducible zip and tar.gz packages and the macOS app tree, `SHA256SUMS`, and the `fluut.releases/1` update manifest (checked on a real Windows build: the zip expands with PowerShell, the tarball lists with `tar`, `sha256sum -c` passes, the `.ico` loads in `System.Drawing`). Both programs write a local crash report on a panic and announce it on the next start; nothing is sent. `release.yml`, `audit.yml` and two new `ci.yml` jobs are written. Gates: 824 tests pass (36 in `xtask`, 8 + 1 for crash reports, 4 for `build_info`, 1 CLI test each for the version and the crash note).

Untested (cannot run here):

The macOS steps (`lipo`, `codesign`, `hdiutil`, `notarytool`, `stapler`), `signtool`, `minisign`, `cargo install cargo-cyclonedx --version 0.5.7` and the SBOM file names it writes (the script searches for `*.cdx.json` or `bom.json`), `gh release create`, and the Linux and macOS builds.

- `repro-check` passes its unit tests but has never reported equal builds: on Windows 20 bytes differ (see Task 5). The Linux result is unknown.
- Nothing signed: no certificate, key or Apple account exists.

Deviations from the brief:
- `if: secrets.X != ''` is not valid in GitHub Actions; the `check` job turns the secrets into outputs and each signing step tests those.
- No MSI, AppImage or Flatpak: they need WiX, `appimagetool` and Flathub work that cannot be tested here. Windows ships a zip, Linux a tar.gz, macOS a DMG. D14 §5.2 lists them as not yet built; `packaging/` is not created.
- ICO and ICNS are written by hand around PNGs; no `ico` or `icns` crate.
- The window icon was already rendered from the SVG by `fluut-app`'s build script (M5), so it is unchanged. The `.exe` file icon needs a resource compiler and is not set.
- The `docs` job does not use `-D warnings`: three rustdoc link warnings exist (`fluut-topo` `pcurve.rs`, `fluut-model` `project.rs`, `fluut-io-2d` `svg.rs`; the last is in a crate I may not edit).
- No MSRV job (`rust-version` equals the pinned toolchain); no nextest, determinism, bench, fuzz or ui jobs (not cheap).
- Crash reports have no last log lines (the code has no logging) and no native crash handler. `fluutcam` writes the next-start note to stderr; the in-window dialog needs translated texts in `text.rs`, which the i18n work owns.
- Release profile needed no change; CFG and path remapping come from `cargo xtask rustflags` rather than `.cargo/config.toml`, because `RUSTFLAGS` would override the config.

Secrets the product owner must provide: superseded on 2026-11-01. Windows signing now goes through SignPath and macOS stays ad hoc; the current repository settings are listed in D14 §5.2.

Decisions the product owner must make:
- The macOS bundle identifier (`io.github.fluutcam.FluutCAM` for now) and whether a domain exists for a reverse-DNS one.
- The Authenticode time-stamp server (DigiCert's is in the workflow) and whether to sign through a service or an HSM instead of a PFX file.
- Whether to build an MSI, AppImage and Flatpak, and who owns the Flathub entry.
- Release channels and update cadence, and the telemetry policy (spec 06 §6.5); the crash-report endpoint and opt-in flow before any sending code is written.
- Minimum OS values (`windows-10`, `macos-11.0`, `glibc-2.35`) and whether Linux builds on Ubuntu 22.04.
- Whether releases stay drafts (current) or publish automatically once signed.
