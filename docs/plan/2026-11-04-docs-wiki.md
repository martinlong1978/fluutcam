# User Documentation Wiki Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** User documentation as a GitHub wiki, for new users and for user acceptance testing (UAT). The pages are written in the main repository (`docs/wiki/`), reviewed with the code, and mirrored to the wiki repository by a workflow. Screenshots and the reference pages are generated, so they grow with the UI instead of going stale.

**Architecture:**

- `docs/wiki/*.md`: the pages, in GitHub wiki naming (`Home.md`, `_Sidebar.md`, `_Footer.md`, ...), images in `docs/wiki/images/`. Hand-written pages and generated pages sit side by side; a generated page starts with a comment saying so.
- `.github/workflows/wiki.yml`: on a push to `main` that touches `docs/wiki/**` (and on `workflow_dispatch`) it clones `<repo>.wiki.git` with the built-in `GITHUB_TOKEN`, `rsync --delete`s the folder in, commits and pushes. No third-party action beyond `actions/checkout`, no secret.
- `crates/fluut-app/examples/screenshots.rs`: renders the real app headless with `egui_kittest` (wgpu snapshot renderer, so the 3-D viewport is included) from reference projects, at a fixed size, dark theme, into `docs/wiki/images/`. The list of shots is one table in the code. `cargo xtask screenshots` runs it. It is an example of `fluut-app`, not code of `xtask`, because `xtask` is outside the crate layers and must stay light (D01 §1).
- `crates/fluut-model/examples/wiki_reference.rs`: writes `Toolpath-Types.md` and `Diagnostics.md`. The toolpath pages come from the D15 field tables in `fluut-model` (`ToolpathTypeId::fields`), the labels in the Fluent catalogs, and the descriptions and ranges in `docs/design/D15*.md`. The diagnostics page comes from a scan of the `Diagnostic::error` and `Diagnostic::warning` calls in `crates/*/src`, plus a table of advice in `docs/wiki/reference/advice.toml`. `cargo xtask wiki-reference [--check]` runs it; `--check` fails when a file differs. CI runs the check in the `lint` job.

**Design:** [D13](../design/D13-ui-architecture.md) §10 (UI tests), [D14](../design/D14-build-test-release.md), [D15](../design/D15-toolpath-parameters.md), [D15b](../design/D15b-toolpath-parameters-2.md), [D12b](../design/D12b-scripting-api.md).

## Global Constraints

All earlier Global Constraints apply. In addition:

- Never document what is not there. Each statement about behaviour is checked against the code or by running `fluut` or the app. A planned feature is "not yet", in those words.
- Plain English for a hobbyist or small-shop machinist: short sentences, active voice, each CAM term defined once. No crate names outside the developer pages.
- No content derived from DeskProto: no text, names, screenshots or workflows.
- The ribbon is being rebuilt. Pages use the temporary File menu where the ribbon would be, say the ribbon will replace it, and keep other words about the ribbon light. Screenshots are regenerated when it lands.
- Screenshots are deterministic: fixed size, dark theme, fixed clock, no absolute paths on screen, software rasteriser preferred (`egui_kittest`'s default adapter order). PNGs are optimised; the folder stays under a few MB.
- The workflow never runs on pull requests and uses no secret; only `contents: write` through `GITHUB_TOKEN`.

## Decisions

1. **Headless rendering works with the viewport.** `egui_kittest`'s `wgpu` feature renders a frame to an image from a shared `RenderState`, so the viewport callback (the app's own `wgpu` pipeline) draws into the shot. The default `egui_kittest` instance includes the OpenGL backend, whose WGL thread overflows its stack in debug builds on Windows; the example asks for the primary backends (Vulkan, Metal, DX12) only.
2. **Shots are driven through the job layer, not through the file dialogs.** A native dialog cannot run headless; the example calls the `Jobs` methods the dialogs call (`new_project`, `import_model`, `add_setup`, ...). Menus are opened by clicking their labels, so the shot shows the real menu.
3. **Reference pages from data, not from prose.** The field metadata gives key, unit, default and group; the D15 tables give range and "depends on"; a short help text per field (`docs/wiki/reference/help.toml`) gives the meaning where the tables only give a range. A field with no help text shows its D15 range and dependencies.
4. **Diagnostics come from the source.** There is no list of codes in the code. The generator scans for the constructor calls, takes the first string literal as the code and the next string (or `format!` string) as the message, shows `{...}` placeholders as `...`, and for a code built at run time (`cam.{ty}.tool_shape`) writes `<type>`. Advice comes from `advice.toml`: exact code, else the longest matching prefix.
5. **UAT pages are manual test scripts.** One page per area, tests with id, preconditions, steps, expected result and a `- [ ] Pass` box, so a tester copies the page into an issue or a spreadsheet. Test files are the reference projects in `crates/fluut-cli/tests/projects/`.

## Open issues

- The wiki workflow can only be verified in CI: the wiki must be enabled and one page created by hand so the wiki repository exists.
- The window cannot pick curves or faces, so 2-D toolpath pages and tests rely on project files; they change when picking lands.
- The ribbon is being rebuilt by another agent. Pages use the File menu and name ribbon buttons lightly. Rerun `cargo xtask screenshots` and review the pages after that merge.
- Found and fixed along the way: the app's Messages used the wrong Setup kind for rotary checks, and `fluut run` failed with a bare project file name.
- UAT pages are written from the code and `fluut` runs. The window tests have not been run by a human; the first tester may find wording to fix.
- STL import gives no bodies, DXF/SVG need curve picking, and two files with the same body ids cannot share a project. All are in Known-Limits.
