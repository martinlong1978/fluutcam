# M5 — UI v1 Shell Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The first FluutCAM window. Exit criterion from the roadmap: open, calculate and post a reference project from the UI.

**Architecture:** One new crate, `fluut-app` (layer 8, binary `fluutcam`), in the layers of D13 §1:
- **Session adapter** (`session.rs`). The only module that calls `fluut-core`. M4 replaces `fluut-core`'s session with `Session::apply`, undo and the journal; this module is where that rebase happens. It owns the `Session` on a worker thread and turns UI requests (open, edit, calculate, post, cancel) into calls on today's API.
- **Job layer** (`jobs.rs`). Requests and events over channels; a `CancelToken` and atomic progress per job (D01 §3). The UI thread never runs a job. The UI holds an immutable `Snapshot` (project, statuses, results, display scene) that the worker replaces after each step (D01 §3.1: snapshots, not locks).
- **View models** (`vm/`). Toolkit-independent and tested without a window: `TreeVm` (Setups and toolpaths with status icons), `InspectorVm` (fields from the D15 metadata), `RibbonVm` (commands and whether they are enabled), `StatusVm` (job progress).
- **Viewport** (`viewport/`). Promoted from `spikes/s4-common`: the orbit camera and the `wgpu` renderer, now drawing the Setup's faces in the work frame, edges, wires, the stock box and the toolpaths, with an on-demand ID pass for picking (D13 §5.2).
- **Widget layer** (`ui/`). `eframe` + `egui_dock` (OQ-09): title bar, ribbon, browser, viewport, inspector and a job strip, in dock tabs. Themes and fonts from the brand (D13 §6–§6.1).

**Tech Stack:** `eframe`/`egui` 0.36 (features `accesskit`, `wgpu`, `wayland`, `x11`; no `default_fonts`), `egui_dock` 0.21, `wgpu` 30, `bytemuck`; `resvg` 0.49 (no default features) as a build dependency for the icon and logo; `egui_kittest` 0.36 for tests.

**Design:** [D13](../design/D13-ui-architecture.md) (all), [D01](../design/D01-workspace-architecture.md) §3–§6, [D15](../design/D15-toolpath-parameters.md) §1, §6, [D14](../design/D14-build-test-release.md) §5.2; spec [08](../spec/08-user-interface.md); [S4 report](spikes/s4-ui-toolkit.md).

## Global Constraints

All earlier Global Constraints apply. In addition:

- Every commit passes `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo xtask check-layers` and `cargo deny check`.
- `fluut-app` depends only on lower layers. It does not edit `fluut-model` or `fluut-core` internals (M4 runs in parallel), nor `fluut-cam`, `fluut-io-*`, `fluut-sim` or `third_party/`. A small API, if one is needed, gets its own commit and a line in the Done note.
- Determinism (D01 §6): the G-code the UI writes is made by `Session::post`, exactly as the CLI does; the UI adds nothing to outputs. Display code may use `f32` and platform maths.
- Generated rasters are never committed (D14 §5.2, `assets/README.md`).
- No content derived from DeskProto.

## Scope decisions

- **Session API.** `fluut-core` today has a synchronous `Session` with `calculate(&Targets)` and `post`, no job ids, events, progress or cancel, and no `apply(Edit)`. The adapter builds the D01 §3 job surface on top: one calculation job runs its toolpaths one at a time (`Targets::Toolpaths([id])`), reports progress after each, and checks its `CancelToken` between them. Cancel latency is therefore one toolpath until `fluut-cam` checks the token inside strategies (D01 §3).
- **Edits.** Inspector changes become `Edit::SetParam { toolpath, path, value }` and are applied by the adapter with `Params::set` on `Session::project`. There is no undo until M4 (`Session::apply`).
- **Save.** Not in M5: saving the `.fluut` file needs M4's writer path and undo. The ribbon shows Open, Calculate, Post and Cancel.
- **`visible_if`.** D15 §6 leaves `visible_if` for the inspector. It is not in `FieldMeta`, and adding it touches every table M4 is editing. M5 keeps the rules from the D15 "Depends on" columns in `vm/visible.rs`, keyed by field path, to move into `fluut-model` after M4 merges.
- **Labels and messages.** There is no `fluut-i18n` crate yet (layer 1 in `xtask/layers.toml`, not created). Every user-visible string goes through `text::tr(id)`, a table of English messages keyed by Fluent ids (`ribbon-open`, `param-step_down-label` from `FieldMeta::label_id`, diagnostic ids from `Diagnostic::fluent_id`). A pseudo-locale (D13 §9) wraps every message, so a test catches strings that bypass the table. Swapping the table for `fluut-i18n` is a follow-up.
- **Display tessellation.** `fluut-topo` has no display mesh yet (D03 §7). The viewport samples each face on a (u, v) grid clipped to the trim loops' polylines (`fluut_topo::trim::loop_polyline`), so face borders are stepped at grid resolution; the exact edges are drawn on top as lines. Proper trimmed tessellation belongs to `fluut-topo` later.
- **Frame.** The viewport shows the selected Setup in its work frame W (`fluut_core::SetupFrame`): bodies, stock box, work zero and that Setup's toolpaths. Toolpath results are already in W.
- **Font.** Noto Sans Regular (OFL-1.1), one file in `crates/fluut-app/assets/fonts/` with `OFL.txt`. It is the proportional and the monospace family; a monospace face for a G-code panel comes with that panel.
- **Icon and logo.** `build.rs` renders `assets/fluut-D-icon-stock.svg`, `fluutcam-D-logo.svg` and `fluutcam-D-logo-dark.svg` with `resvg` into RGBA in `OUT_DIR`; the binary includes those bytes. Nothing generated is committed.
- **Timeline, command palette, handles, stages other than the ribbon tabs**: after M5.

## Review Focus

1. **The UI thread never blocks on a job.** Open, calculate and post run on the worker; the UI only reads snapshots and atomics.
2. **Same G-code as the CLI.** The headless test compares the app's post output with `fluut post` byte for byte.
3. **The adapter is thin.** Only `session.rs` names `fluut_core::Session`; M4's rebase touches one file.
4. **No hard-coded UI text.** Strings come from `text.rs`; the pseudo-locale test proves it for the view models.

### Task 3: Job layer and session adapter

**Files:** Create `crates/fluut-app/src/{jobs.rs, session.rs, scene.rs}`.

- `jobs.rs`: `CancelToken`, `Progress` (atomics: done, total, current toolpath), `JobId`, `Request`, `Event`, and `Jobs` (the UI's handle: sends requests, drains events without blocking).
- `session.rs`: the worker loop. `Open(path)` → `Session::open`, display scenes, a snapshot. `Calculate(targets)` → one toolpath at a time with progress and cancel. `Post { post, out, opts }` → `Session::post`, then the files written next to `out` as the CLI names them. `Edit(SetParam)` → `Params::set` and a new snapshot.
- `scene.rs`: per Setup, from `SetupFrame`: face triangles with face ids, edge and wire polylines, stock box, work zero; per toolpath, polylines with a motion per vertex (arcs linearised with `fluut_path::linearize`).
- Status per toolpath (S 08 §8.6): not calculated, calculating, done, stale (calculated earlier, inputs changed), warning, error.

### Task 4: View models

**Files:** Create `crates/fluut-app/src/vm/{mod.rs, tree.rs, inspector.rs, visible.rs, ribbon.rs, status.rs}`.

- `TreeVm`: Setups (name, kind) → toolpaths (name, type, status, progress); model bodies; selection.
- `InspectorVm`: for a toolpath, the five groups of S 08 §8.5 as tabs; per field: label, kind (length / feed / speed / angle / count / bool / enum with options / height / selection / point / table rows flattened), value text in the project unit, default text when unset (constant, tool preset with its value, or formula), whether it is set, whether `visible_if` shows it, and its diagnostics (from `validate`, matched by `Diagnostic::field`). For a Setup: its fields, read-only.
- Entry: `parse_entry(field, text, unit, tool)` accepts a number, a unit suffix (`mm`, `in`, `"`), simple arithmetic and `tool.diameter`/`tool.radius`/`tool.corner_radius`/`tool.flute_length` (D15 §1.6), and returns the `Edit`.
- `RibbonVm`: Open (always), Calculate (project open, no job), Post (project open, no job), Cancel (job running).
- `StatusVm`: running job label and fraction; last result message.
