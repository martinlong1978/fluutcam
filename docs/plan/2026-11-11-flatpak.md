# Flatpak Plan

**Goal:** Ship a Flatpak for Linux, as [D14 §5.2](../design/D14-build-test-release.md) and [spec 06](../spec/06-security-and-distribution.md) plan. Step one is a single-file bundle (`fluutcam-<version>-linux-x86_64.flatpak`) in every GitHub release, made from the same prebuilt binaries as the tarball and the AppImage. Step two, a build from source for Flathub, is described in "Flathub source build" below.

**Design:** [`../design/D14-build-test-release.md`](../design/D14-build-test-release.md) §5.2.

## Decisions

1. **App id `io.github.martinlong1978.FluutCAM`**, from the GitHub repository, the form Flathub accepts for a project hosted on GitHub. The application keeps its window class `fluutcam`; the launcher sets `StartupWMClass=fluutcam` so the window still matches it.
2. **Runtime `org.freedesktop.Platform` 24.08.** The application is egui on wgpu with Wayland and X11 windows; it needs no toolkit (rfd uses the xdg portal, not GTK), so the plain freedesktop runtime is enough: it brings Mesa, the Vulkan loader, libwayland, libxkbcommon and the X11 libraries the binary loads at run time. The binary is built on Ubuntu 22.04 (glibc 2.35) and the runtime has a newer glibc, so it runs. The rust-stable SDK extension is **not** used: nothing is compiled in the Flatpak build (see 6).
3. **Permissions, as few as work:** `--socket=wayland`, `--socket=fallback-x11`, `--share=ipc` (X11 shared memory), `--device=dri` (GPU). No `--filesystem`: the file dialogs are `rfd` with the `xdg-portal` feature (already on in `crates/fluut-app/Cargo.toml`, no GTK, so no Cargo change was needed), so the dialogs are the portal's and hand the application the files that are picked. No D-Bus names are needed for the portal (it is reachable from every sandbox). Settings and crash reports go to the sandbox's `XDG_DATA_HOME`, `~/.var/app/<id>/data/fluutcam`.
4. **No network.** The only network use is the opt-in update check to `github.com` ([PRIVACY.md](../../PRIVACY.md)). A Flatpak is updated by Flatpak, never by the application, and no build has an update key yet, so `--share=network` buys nothing but a bigger permission. Without it the check fails with its usual "update check failed" message if a person turns it on. If that ever matters, adding `--share=network` is one line in the manifest and one row in the privacy policy.
5. **Known cost of no filesystem access:** a project that refers to a model file beside it (not only the file picked in the dialog) cannot read the model. `flatpak override --user --filesystem=<folder>` fixes it and is in the install page; the AppImage and tarball are not sandboxed. If this matters in practice, a broader default (`--filesystem=home`) is the alternative, at the cost of the sandbox. UAT-INS-03 checks what happens.
6. **Prebuilt binaries, not a source build.** `packaging/flatpak/build-flatpak.sh` unpacks the Linux tarball into `payload/`, and the manifest copies `bin/`, icons and licences out of it (`type: dir` source, `buildsystem: simple`). The Flatpak therefore contains exactly the bytes of the tarball's executables, which are the ones attested and checksummed.
7. **Packaging tool:** the `flatpak/flatpak-github-actions/flatpak-builder` action in the `ghcr.io/flathub-infra/flatpak-github-actions:freedesktop-24.08` container (privileged, for bubblewrap), which runs `flatpak-builder` and `flatpak build-bundle` with the Flathub runtime repository named in the bundle, so `flatpak install --user <file>` fetches the runtime. The action and image are pinned by tag.
8. **Self-checking CI.** Before the build `validate.sh` runs `desktop-file-validate` and `appstreamcli validate --no-net` on the launcher and metainfo. `build-flatpak.sh` fails (for a version without a pre-release suffix) when the metainfo has no `<release>` for the version being built, so a release cannot go out with a stale entry. After the build `smoke-test.sh` installs the bundle for the user, runs `fluut --version` inside the sandbox, checks the permissions (Wayland and DRI present; no network, no filesystem, no D-Bus names, no `devices=all`) and uninstalls it.
9. **Release plumbing:** `package-flatpak` in `release.yml` (needs `package-portable`) uploads `dist-flatpak`, which the `release` job's `dist-*` pattern picks up: it is checksummed (`SHA256SUMS`, which is minisigned), attested and attached to the draft release. In a dry run (a `workflow_dispatch` on a branch) it is in `dry-run-dist`. `packaging.yml` has a `flatpak` job (with `flatpak-input`, which builds the tarball) for pull requests that touch `packaging/`. `releases.json` does not list the bundle: `cargo xtask manifest` ignores kinds it does not know, and the in-app update check offers nothing for a Flatpak install anyway.
10. **Not signed by us.** A bundle has no GPG signature (no key). Trust comes from the attestation and checksums; Flathub (later) signs the repository it serves.

## Follow-up: Flathub (original notes; steps 1 to 3 are done, see "Flathub source build")

Flathub builds every app from source, offline, with the SDK:

1. Generate `generated-sources.json` for `Cargo.lock` with `flatpak-cargo-generator.py` (from `flatpak/flatpak-builder-tools`, `cargo/`), and add the `org.freedesktop.Sdk.Extension.rust-stable` SDK extension (`sdk-extensions`, `append-path: /usr/lib/sdk/rust-stable/bin`, `CARGO_HOME=/run/build/fluutcam/cargo`, then `cargo --offline build --release --locked -p fluut-cli -p fluut-app`).
2. Use a `type: git` source with a tag and commit for the repository, so the manifest builds a tagged release.
3. Check the `third_party` crates and any build script or `git` dependency that needs the network (the generator vendors registry crates; git dependencies need entries of their own).
4. Submit the manifest to `flathub/flathub` as a new-app pull request; it must pass `flatpak-builder-lint` (add that to CI first) and the screenshots must resolve.
5. Keep one `<release>` per version in the metainfo; the 0.1.0 date is a placeholder for the real release day.
6. Pre-releases (`-beta.N`, `-rc.N`) go to a `beta` branch of the Flathub app repository, which Flathub publishes to the `beta` Flatpak branch; the stable default branch carries stable releases only ([D17](../design/D17-telemetry-and-channels.md) §3.5). The in-app update check does not run in the sandbox, so the app's release channel setting does not apply to a Flatpak.

The metainfo, launcher, icons and permissions in `packaging/flatpak/` carry over unchanged.

## Flathub source build (2026-11-12)

**Goal:** a manifest Flathub accepts, built from source offline, without changing the bundle in GitHub releases.

**Decisions**

1. **Two manifests, kept.** `io.github.martinlong1978.FluutCAM.yml` (prebuilt binaries, `type: dir`) still makes our `.flatpak` bundle; the new `io.github.martinlong1978.FluutCAM.flathub.yml` is the Flathub one. One source manifest could serve both, but the bundle would then be a fresh compile in the sandbox, not the bytes of the tarball that are attested and checksummed (decision 6 above), and every release would pay a full vendored compile instead of a copy. So the release path is unchanged and the source manifest is a parallel build that only Flathub uses (and CI dry-runs).
2. **Toolchain:** `org.freedesktop.Sdk.Extension.rust-stable` on runtime 26.08 (24.08, now end of life, ships rustc 1.89; the extension is now used; decision 2 above said it was not needed while nothing was compiled). `rust-toolchain.toml` does not apply (no rustup); the workspace needs Rust 1.99.
3. **Vendored crates:** `cargo-sources.json`, made by `flatpak-cargo-generator.py` from `flatpak/flatpak-builder-tools`, pinned by commit (`41c20aa10819cdb2a4f3ca171758a96d1955c018`) and SHA-256 in `packaging/flatpak/update-cargo-sources.sh`. The script downloads only that file, runs it with `python -I` in a virtualenv and normalises line endings. `Cargo.lock` has no git dependencies; the one patched crate (`third_party/cavalier_contours`) is a path dependency in the checkout. The output follows from the `Cargo.lock` checksums.
4. **Build:** `cargo --offline build --release --locked -p fluut-app -p fluut-cli`, then `cargo --offline run --release --locked -p xtask -- icons icons` for the icons, then install the two binaries, licences, launcher, metainfo and the eight hicolor icons. Permissions unchanged: Wayland with X11 fallback, ipc, dri; no network, no filesystem.
5. **Pinned git source.** The manifest's source is the repository at a release tag and commit, as Flathub needs. v0.1.0 predates the source manifest, so `tag` and `commit` are marked placeholders until a later release; `FLATHUB.md` says how to set them. The CI dry run replaces the `git` source (between `release-source` markers) with the checkout using `stage-source-build.sh`, so the same manifest text is built.
6. **CI guard:** `update-cargo-sources.sh --check` runs in the `flatpak-sources` job of `ci.yml` (every push and pull request) and in `flathub-source`; a `Cargo.lock` change without regenerating `cargo-sources.json` fails.
7. **Dry run:** job `flathub-source` in `packaging.yml` (pull requests touching `packaging/`, and on demand): `validate.sh`, `--check`, `flatpak-builder-lint` on the manifest, `flatpak-builder --repo`, `flatpak-builder-lint` on the repository, bundle, `smoke-test.sh`, in the same pinned container. Nothing is uploaded or published.
8. **Channels:** unchanged from D17 section 3.5; pre-releases go to a `beta` branch of the Flathub app repository.
9. **User-facing:** nothing changes for people yet (`docs/install.md` and the wiki Install page still say the Flatpak is not on Flathub, which stays true until the submission is accepted).
